# Architecture

> Narrative description of the as-deployed v4 architecture. For canonical
> detail, see `docs/design/2026-05-04-workspace-consolidation.md` and the ADRs
> under `docs/adr/`.

## Intent

dotpanel separates universal agent methodology (public, reusable) from operator
identity (private, per-person) from project-specific truth (per-repo). The
boundary between these three concerns is structural — different repositories,
different audiences, different sync owners — not enforced by lint rules inside
one tree.

## Three Layers

| Layer | Lives in | Scope | Sync owner |
|---|---|---|---|
| **protocol** | `~/src/dotpanel/` (this repo, public) | Universal methodology, Python CLI, reference library, harness templates | anyone fork/install |
| **persona** | `~/.dotfiles/persona/` (private) | Operator **data**: voice, identity yaml, machine-setup data, keyword-router rules, private reference. **Cross-project only**; project-scoped content lives in `{project}/.agents/`. No methodology, no program logic, no runtime state — runtime (active runs, journal) lives at the project layer. | operator across machines |
| **project** | `{project}/.agents/` | Per-project conventions, run handoffs, decisions, project-scoped memory | collaborators on that project |

Protocol says **how** agents work. Persona says **who** the operator is and how
they collaborate. Project `.agents/` says **what** is true for a specific
codebase. Each layer is owned by a different audience and synced through a
different mechanism.

## Two-Repo Split

The split that matters for publication is between dotpanel (public) and the
operator's private persona home:

- **`~/src/dotpanel/` — public.** The dotpanel repo. Contains
  protocol/, harness/, dotpanel/ (the Python package), docs/. Born public; no
  privacy mechanism inside the repo to flip. A fork operator can install it,
  bring their own persona, and run.
- **`~/.dotfiles/persona/` — private.** Tracked privately by the
  operator's existing dotfiles repo. Contains voice.md, identity.yaml,
  rules/, reference/, runtime/. Never enters the public repo as content;
  reachable from dotpanel only through the symlink bridge described below.
  Single operator per persona directory — no `<slug>/` indirection.

Harness homes (`~/.claude/`, `~/.codex/`, `~/.kimi/`) are not source repos in v4. They are
**rendered output directories** — `dotpanel configure` writes them; the harness
itself reads them at runtime. Their contents are reproducible from
dotpanel + persona at any time.

## Persona Symlink Bridge

`dotpanel/persona` is a gitignored symlink pointing at the operator's private
persona directory:

```text
~/src/dotpanel/persona  ->  ~/.dotfiles/persona/
```

This single bridge lets dotpanel read voice/identity/runtime data through
dotpanel-relative paths (e.g. `protocol/skills/...` and `persona/voice.md`
both resolve under one root) without the public repo ever tracking persona
content.

Symlink properties:

- `.gitignore` excludes `/persona`, so `git status` never sees it
- `MANIFEST.in` carries `prune persona`, so `python -m build` never includes it
- `dotpanel doctor` verifies the symlink exists and the target is a directory
- `dotpanel audit` re-verifies the invariant in CI/pre-commit context

The symlink is created by `dotpanel init [--persona-root <path>]`. Default
discovery looks for `~/.dotfiles/persona/`; the flag lets a fresh operator
point at any persona directory they own.

## File Class Taxonomy

Every file under dotpanel + persona belongs to exactly one of three classes:

| Class | Definition | Examples | Owner |
|---|---|---|---|
| **Rendered** | Generated by `dotpanel configure` from a template. Carries a `<!-- Generated by dotpanel; do not edit directly. -->` banner where the format permits comments. | `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.kimi/AGENTS.md`, `~/.claude/skills/<name>/SKILL.md` (skill wrappers), `~/.claude/settings.json` (banner-less, listed in `DOTPANEL_MANAGED_JSON`) | dotpanel writes; do not hand-edit |
| **Symlink** | Explicit OS bridge between layers. | `~/src/dotpanel/persona -> ~/.dotfiles/persona` | dotpanel creates via `init`; tracked in `protocol/rules/symlink-registry.md` |
| **Source** | Canonical authored content. Edited by humans; read by configure (as templates) or directly at runtime (e.g. through wrapper references). | `protocol/skills/*.md`, `protocol/workspace.md`, `persona/voice.md`, `harness/*/templates/*` | the layer's owner edits directly |

There is no separate Wrapper class — wrappers are rendered files. There is no
broad Runtime class — ADR-3 specifies the exact runtime paths configure
refuses to touch (`~/.claude/sessions`, `~/.codex/*.sqlite`, `~/.kimi/logs`, etc.).

The three-class taxonomy is enforceable: a file is either generated (banner or
managed-list), a symlink (`is_symlink()`), or source (everything else).

## Cross-Layer Interaction

The three layers cooperate through documented seams. Each seam has one
producer and one consumer:

| Seam | Producer | Consumer | Mechanism |
|---|---|---|---|
| Active-run manifest | project `.agents/runs/active.yaml` | `/wrap` (writes), agent at runtime (reads) | source of truth for run owner, scope, status, revision |
| Run handoff | project `.agents/runs/<name>/handoff.md` | `/wrap` skill | self-describing resume pointer; readable with or without dotpanel installed |
| Project journal | `{project}/.agents/journal/diaries/<date>-<topic>.md` | `/wrap` skill | per-day record scoped to one project |
| Cross-project journal | central-node repo's `.agents/journal/diaries/` | `/wrap` skill | per-day record for cross-cutting work; operator designates the central node in their persona |
| Project memory | project `.agents/memory/` | agent at runtime in that project's cwd | project-scoped facts; travels with the project |

Runtime state lives in the **project layer**. Each project owns its own
`.agents/runs/`, `.agents/journal/`, and `.agents/memory/`. Persona is
data only — no runtime, no active-run index, no journal. Cross-project
work goes to the operator's chosen central-node repo's `.agents/`.

A project handoff is intentionally self-describing: the `handoff.md` includes
enough context (status, last verified commands, next steps) that a fresh
collaborator who clones only the project repo can resume without having
dotpanel or the operator's persona.

## Referencing Wrapper

`dotpanel configure` generates `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, and `~/.kimi/AGENTS.md`
as a thin wrapper. The wrapper carries absolute paths to:

1. `<dotpanel-root>/persona/voice.md`
2. `<dotpanel-root>/protocol/workspace.md`

The wrapper instructs the agent to read both files in order at session start.
Editing `voice.md` or `workspace.md` takes effect on the next agent session
without reconfigure. Reconfigure is only needed for **structural** changes:
new skill, changed harness path, changed template, or changed `dotpanel-root`.

## CLI Boundary

The Python package surface is documented in
`docs/design/2026-05-04-workspace-consolidation.md` under "CLI Surface". The
short version:

| Command | Purpose |
|---|---|
| `dotpanel root` | Print absolute path to install root |
| `dotpanel doctor` | Verify install, symlink, persona, templates, paths |
| `dotpanel audit` | Structural invariants for CI/pre-commit |
| `dotpanel init [--persona-root <path>]` | Create persona symlink and run doctor |
| `dotpanel configure --harness {claude\|codex\|kimi\|all}` | Render adapters into harness homes |
| `dotpanel uninstall --harness {claude\|codex\|kimi\|all}` | Remove banner-marked files (preserves runtime data) |

Exit codes: 0 ok, 2 validation failure, any other non-zero is a crash.

## Independence

`dotpanel` does not depend on `dot`, `secrets`, `bootstrap`, or
`machines.yaml` — those are operator-private substrate that lives in the
operator's dotfiles. dotpanel reads `os.environ` for any required secret values
(LLM API keys, etc.); secret management is the operator's private concern.

`dot` may call `dotpanel` (for example, `dot pull` runs `dotpanel configure
--check` and then real configure if check passes). `dotpanel` never calls `dot`.
