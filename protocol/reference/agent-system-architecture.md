# Agent System Architecture

This file is universal cross-project agent infrastructure knowledge. Anyone forking dotpanel or building on top of it reads it. For canonical detail, see `{{DOTPANEL_ROOT}}/docs/architecture.md` and the ADRs under `{{DOTPANEL_ROOT}}/docs/adr/`.

## Three Layers

| Layer | Lives in | Scope | Audience |
|---|---|---|---|
| **protocol** | `{{DOTPANEL_ROOT}}/` (public dotpanel repo) | Universal methodology, Python CLI, reference library, harness templates | anyone fork/install |
| **persona** | the operator's persona host (operator-private repo) | Operator **data**: voice, identity, machine-setup data, keyword-router rules, private reference. Cross-project only; project-scoped content lives in `{project}/.agents/`. No methodology, no program logic, no runtime state — runtime lives at the project layer. | one operator across machines |
| **project** | `{project}/.agents/` (per-project subtree) | Per-project conventions, run handoffs, decisions, project-scoped memory | collaborators on that project |

Protocol says **how** agents work. Persona says **who** the operator is and how they collaborate. Project `.agents/` says **what** is true for a specific codebase. Each layer is owned by a different audience and synced through a different mechanism. The boundary is **structural** — different repos, different audiences, different sync owners — not enforced by lint rules inside one tree.

## Persona Symlink Bridge

The dotpanel repo carries a single gitignored symlink:

```text
{{DOTPANEL_ROOT}}/persona  ->  <operator's persona host directory>
```

Created by `dotpanel init [--persona-root <path>]`. This bridge lets dotpanel read voice/identity/runtime data through dotpanel-relative paths without the public repo ever tracking persona content. Properties:

- `.gitignore` excludes `/persona`, so `git status` never sees it
- `MANIFEST.in` carries `prune persona`, so dist artifacts never include it
- `dotpanel doctor` verifies the symlink target is a directory
- `dotpanel audit` re-verifies the invariant in CI/pre-commit context

## File Class Taxonomy

Every file under dotpanel + persona belongs to exactly one of three classes:

| Class | Definition | Examples | Owner |
|---|---|---|---|
| **Rendered** | Generated by `dotpanel configure` from a template. Carries a `<!-- Generated by dotpanel; do not edit directly. -->` banner where the format permits comments. | `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, harness skill wrappers, `~/.claude/settings.json` (banner-less, listed in `DOTPANEL_MANAGED_JSON`) | dotpanel writes; do not hand-edit |
| **Symlink** | Explicit OS bridge between layers. | `{{DOTPANEL_ROOT}}/persona` → operator's persona host | dotpanel creates via `init`; tracked in `{{DOTPANEL_ROOT}}/protocol/rules/symlink-registry.md` |
| **Source** | Canonical authored content. Edited by humans; read by configure (as templates) or directly at runtime (e.g., through wrapper references). | `{{DOTPANEL_ROOT}}/protocol/skills/*.md`, `{{DOTPANEL_ROOT}}/protocol/workspace.md`, `{{DOTPANEL_ROOT}}/persona/voice.md`, harness templates | the layer's owner edits directly |

There is no separate Wrapper class — wrappers are rendered files. There is no broad Runtime class — ADR-3 specifies the exact runtime paths configure refuses to touch (`~/.claude/sessions`, `~/.codex/*.sqlite`, etc.).

The taxonomy is enforceable: a file is either generated (banner or managed-list), a symlink (`is_symlink()`), or source (everything else).

## Configure Protocol

`dotpanel configure` renders harness adapters into harness home directories:

| Flag | Behavior |
|---|---|
| `--check` | Dry-run validator: templates parse, placeholders resolve, target paths legal, `dotpanel doctor` passes |
| `--force` | Cutover overwrite of pre-existing non-banner files |
| `--output-dir <path>` | Sandbox output for tests and migration rehearsals |
| `--harness {claude\|codex\|all}` | Limit render to one harness or render both |

Exit codes: `0` ok, `2` validation failure, any other non-zero is a crash. Writes are per-file transactional (render → temp file in target dir → atomic move). Multi-file all-or-nothing rollback is out of scope.

Harness home directories (`~/.claude/`, `~/.codex/`) are **rendered output**, not source repos. They are reproducible from dotpanel + persona at any time. Configure refuses to touch the runtime paths declared in ADR-3.

## Cross-Layer Seams

Each layer talks to the others through documented seams. One producer, one consumer per seam:

| Seam | Producer | Consumer |
|---|---|---|
| Active-run manifest | project `.agents/runs/active.yaml` | `/wrap` skill (writes), agent at runtime (reads) |
| Run handoff | project `.agents/runs/<name>/handoff.md` | `/wrap` skill |
| Project journal | `{project}/.agents/journal/diaries/<date>-<topic>.md` | `/wrap` skill |
| Cross-project journal | central-node repo's `.agents/journal/diaries/` (operator designates the central node in their persona) | `/wrap` skill |
| Project memory | project `.agents/memory/` | agent at runtime in that project's cwd |

Runtime state lives at the **project layer** — each project owns its own `.agents/runs/`, `.agents/journal/`, and `.agents/memory/`. Persona carries no runtime. Cross-project work that doesn't naturally belong to one project gets recorded in the operator's chosen central-node repo's `.agents/`. A project handoff is self-describing — a fresh collaborator who clones only the project can resume without dotpanel or any persona.

## Dotpanel Independence

`dotpanel` is a standalone Python package. It does **not** assume any specific operator-private substrate (no specific sync tool, no specific secret manager, no infrastructure inventory). Operators bring their own persona; the only contract is the persona directory shape (`voice.md` + `identity.yaml` at the persona root, with optional `rules/`, `reference/`, `runtime/` subdirs).

For LLM API keys and other secrets, dotpanel reads `os.environ`. Secret management is the operator's private concern; protocol assumes required environment variables are already set before agent launch.
