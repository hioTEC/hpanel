# Harness Bridge

## Purpose

`{{DOTPANEL_ROOT}}/protocol/` is the source of truth. Claude, Codex, Kimi, and
other harnesses are adapters. They may expose startup files or skill wrappers,
but they do not own canonical rules or procedures.

The bridge must make rules reachable without copying the rulebook into every
harness context.

## Load Classes

| Class | Load mode | Home | Rule |
|---|---|---|---|
| Kernel | Always loaded at cold start | `{{DOTPANEL_ROOT}}/protocol/workspace.md` inline | Only facts needed before the first action: identity, voice, secrets, destructive operations, bootstrap, stop rules, SoT boundaries. |
| Router | Always loaded at cold start | `{{DOTPANEL_ROOT}}/protocol/workspace.md` summon table | Trigger -> rule/skill path. If the agent cannot find the next rule from here, the rule is not reachable enough. |
| Gate | Pointer always loaded; body read before changing files or state | `{{DOTPANEL_ROOT}}/protocol/rules/*.md` | Broad work-type gates such as quality, module discipline, design contract, content placement, symlinks, and harness adapters. |
| Specialist | Read only when triggered | `{{DOTPANEL_ROOT}}/protocol/rules/*.md` or `{{DOTPANEL_ROOT}}/protocol/skills/*.md` | Narrow rules such as UI audit, collaboration, ADR template, backend review, or reusable procedures. |

Do not promote a full rule body into `workspace.md` because it feels important.
Promote only the part that must be known before the first tool call.

## Harness Surfaces

### Startup

Startup adapters load the kernel/router:

- Claude: `~/.claude/CLAUDE.md`
- Codex: `~/.codex/AGENTS.md`
- Kimi: `~/.kimi/AGENTS.md`

These are rendered files generated by `dotpanel configure`; they are not symlink
interfaces.

Home-level project discovery is separate: `~/AGENTS.md` may exist because some
harnesses treat the home directory as a project root when launched from `~`.
That file is not rendered by `dotpanel configure` and must not duplicate the
kernel/router already loaded by the harness startup adapter. Keep it to
home-level machine and directory conventions only.

### Official Discovery Calibration

As of 2026-05-13:

- Claude Code: personal skills live at `~/.claude/skills/{name}/SKILL.md`.
  The skill name is directly user-invocable as `/name`. `.claude/commands/*.md`
  remains a legacy-compatible surface, but new workspace adapters must use
  skills because custom commands have been merged into skills.
- Codex: skills are invoked explicitly through `/skills` or `$name`, and may be
  invoked implicitly when the request matches the skill description. User-level
  Codex skills live at `$HOME/.agents/skills/{name}/SKILL.md`; repo-level
  project skills live at `.agents/skills/{name}/SKILL.md`. `~/.codex/` remains
  the Codex config/runtime home, not the user skill home.
- Kimi CLI: the current local setup reads `~/.kimi/AGENTS.md` for startup
  context and discovers shared user-facing skills through Claude's
  `~/.claude/skills/{name}/SKILL.md` surface. Until Kimi exposes a separate
  verified user-skill home, dotpanel only renders the Kimi startup adapter.
- Codex plugins distribute skills through `skills/` and may also bundle apps,
  MCP servers, hooks, and assets. the workspace protocol entries do not rely on
  plugin slash-command files; command files are not the SoT.

### Skills

User-facing skill entries need harness-native wrappers:

- Claude: `~/.claude/skills/{name}/SKILL.md`, invocable as `/name`.
- Codex: `~/.agents/skills/{name}/SKILL.md`, invocable as `$name` or through
  `/skills`.
- Kimi: no dotpanel-rendered skill wrappers until a verified Kimi-native user
  skill directory exists.

The wrapper stays thin and points to the canonical body in
`{{DOTPANEL_ROOT}}/protocol/skills/*.md`.

Generated wrappers must carry an audit-visible update contract:

- `Generated by dotpanel. Do not edit this adapter directly.`
- `Source of truth: {{DOTPANEL_ROOT}}/protocol/skills/{canonical}.md`
- `Update command: cd ~/src/dotpanel && python3 -m dotpanel configure --harness all`

`dotpanel audit` must reject wrappers that lose
the canonical source banner or the update command.

Do not put file-level shared skill symlinks under `~/.claude/skills/*.md`.
Claude's loader expects `skills/{name}/SKILL.md`; file-level symlinks produce
`ENOTDIR` loader warnings and are not a valid adapter.

Internal procedures that are invoked only by other skills do not need
harness-native wrappers. They must remain reachable by canonical path from the
calling skill.

### Commands

Do not add `~/.claude/commands/` for workspace protocol entries. Claude Code
skills already provide the user-facing slash surface.

Do not rely on Codex custom slash commands for workspace protocol entries.
Codex built-in slash commands are a control surface for the session; workspace
workflows are skill entries. If a future Codex plugin command is required for a
real product surface, it must be namespaced, thin, audited, and must not shadow
an existing Codex built-in command or a skill entry.

### Rules

Rules do not need harness-native mirrors. They are reachable through:

1. `workspace.md` kernel/router at startup.
2. `{{DOTPANEL_ROOT}}/protocol/rules/index.md` for load classification.
3. The calling skill, project `AGENTS.md`, or active-run handoff that names the
   specific rule.

Do not copy rules into `.claude/rules/` or `.codex/rules/` unless a future
harness requires a real native rule directory. If that happens, the adapter must
be generated or audited as a mirror, not edited as a second master.

### Tools

Tools are executable or configured surfaces, not markdown declarations. A tool
is available only when at least one of these is true:

- executable is on PATH or named by absolute path
- harness/MCP/plugin configuration registers it
- a skill gives an exact command invocation

Documenting a tool under `{{DOTPANEL_ROOT}}/protocol/` does not make it callable.

## Change Protocol

When adding or changing a rule:

1. Put the canonical body under `{{DOTPANEL_ROOT}}/protocol/rules/`.
2. Add or update its entry in `{{DOTPANEL_ROOT}}/protocol/rules/index.md`.
3. If it is a Gate rule, add a `workspace.md` summon entry or kernel sentence.
4. Do not create harness-local copies.

When adding or changing a user-facing skill entry:

1. Put the canonical body under `{{DOTPANEL_ROOT}}/protocol/skills/`.
2. Add thin wrappers in each harness that supports skill discovery.
3. The wrapper must point to the canonical body and contain no divergent process.
4. Regenerate wrappers through `dotpanel configure --harness all`; do not hand-edit
   generated adapters.

When changing a startup adapter or symlink:

1. Update `{{DOTPANEL_ROOT}}/protocol/rules/symlink-registry.md`.
2. Run `dotpanel audit`.
3. Do not add old-name compatibility links. Let stale callers fail loudly.
