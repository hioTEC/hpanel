# Symlink Registry

Tracked symlinks are allowed only when they are a deliberate harness
interface. They are not compatibility aliases, old names, or a way to avoid
updating callers after a protocol migration.

## v4 state: no tracked symlinks

Under the v4 architecture (public dotpanel + private persona via gitignored
bridge), the `allowed_tracked_symlinks` list is empty. All harness output
files in `~/.claude`, `~/.codex`, and `~/.kimi` are Rendered files (per ADR-2
file class taxonomy), generated by `dotpanel configure` with absolute paths
inside.

The single in-repo symlink (`dotpanel/persona`) is **gitignored** — it lives in
the working tree but never enters version control. It is documented in
`informational_gitignored` for visibility but does not count toward the
"tracked symlinks must be registered" rule.

## Rules

- Every tracked symlink in `dotpanel/` or in any operator-private synced
  configuration repo (e.g., the operator's dotfiles or persona host) must
  appear in `allowed_tracked_symlinks` frontmatter above.
- The registry target must match `readlink(2)` exactly.
- Broken symlinks fail audit.
- A symlink that preserves an old protocol name is disallowed unless the same
  entry names an owner, a sunset condition, and the audit still reports it as
  a temporary compatibility path. Default: update the caller and let stale
  paths fail loudly.
- Adding a new tracked symlink requires a registry entry plus an `audit`
  check that verifies presence + target.

## Why empty is good

An empty `allowed_tracked_symlinks` list means no protocol/persona content
hides behind indirection that future readers have to chase. Files are either
where they appear, or they are generated artifacts (banner-marked) that
configure can reproduce. The single bridge symlink lives outside the tracked
file set, where its scope is `dotpanel/persona/*` resolution at runtime only.
